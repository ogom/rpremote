# 大仙古墳プロジェクトでmrbgemを使う理由

[English](mrbgem_migration.md)

## 結論

大仙古墳プロジェクトのRubyコードは、実行時にファイルシステムから順次読み込まず、ローカルmrbgemとしてPicoRubyファームウェアへ組み込みます。

これは単なるファイル配置の都合ではありません。多数のイルミネーションと、Oximeter、音楽、実行制御をRaspberry Pi Pico 2上で安定して使い、同じ構成を再現できるようにするための設計判断です。

## 解決したい問題

イルミネーションには多数のRubyクラスがあります。これらを実機上で`.rb`として読み込むと、PicoRubyは実行中にコンパイルとSandboxの生成を行います。短いサンプルでは扱えても、長いsetlistを連続実行すると、限られたメモリ、断片化、読み込み処理の寿命に影響されます。

ホストで`.mrb`へ事前コンパイルすれば実機上のコンパイルは避けられますが、ファイルから読み込んだ命令列を、定義したメソッドの利用期間まで安全に保持する必要があります。このプロジェクトで検証したPicoRuby 4.0.3とmruby/cの構成では、連続実行を安定させる方法にはなりませんでした。

## 検討した方法

| 方法 | 利点 | このプロジェクトでの問題 |
| --- | --- | --- |
| 起動時に全`.rb`を読み込む | 実行中の追加読み込みが少ない | コンパイルとメモリ消費が起動時に集中する |
| パターンごとに`.rb`を読み込む | 起動時の負荷を分散できる | 実機コンパイルとSandbox生成が繰り返される |
| `.mrb`を必要時に読み込む | 実機コンパイルを避けられる | 読み込んだ命令列の寿命を実行期間まで保証しにくい |
| mrbgemとして組み込む | ビルド時にコンパイルされ、命令列がファームウェアに保持される | 変更時にファームウェアの再ビルドが必要 |

この比較から、長いsetlistを安定して動かすことを優先し、mrbgemへの組み込みを採用しました。

## mrbgemが適している理由

- Rubyコードをホスト側のビルド工程でコンパイルできる。
- 命令列がファームウェアに保持され、実行時に一時的なSandboxやファイル内容の寿命へ依存しない。
- mrbgem間の依存関係を`mrbgem.rake`で明示できる。
- ルートの`Mrbgems`と`Mrbgems.lock`により、組み込む構成を検査・再現できる。
- 実行時は公開require名だけを読み込み、内部ファイル配置をアプリケーションから隠せる。

## 現在の分割

| mrbgem | 責務 |
| --- | --- |
| `daisenkofun-application` | 設定の検証とコンポーネントの組み立て |
| `daisenkofun-runtime` | 時刻、ログ、イベントループ |
| `daisenkofun-oximeter` | MAX30102の測定とイベント発行 |
| `daisenkofun-musical` | 心拍イベントからPWM音への変換 |
| `daisenkofun-illumination` | LED配置、パターン、setlist、心拍連動表示 |

この分割は、機能ごとの責務を分けながら、組み込み順と依存関係をビルド時に確定するためのものです。利用者向けのmodeと設定は[動作モードと設定](modes.ja.md)を参照してください。

## 読み込み規則

外部からは各mrbgemの公開名だけを読み込みます。

```ruby
require "daisenkofun-application"
```

同じmrbgem内のファイルはビルド時にまとめてコンパイルされるため、`require "daisenkofun-application/config"`のような内部パスを本番コードから個別に読み込みません。別のmrbgemが必要な場合は、`mrbgem.rake`の依存関係として宣言します。

この規則はRSpecのmrbgemロード契約で検証します。

## 開発時の判断

mrbgemのRubyコード、`mrbgem.rake`、ルートの`Mrbgems`を変更した場合は、ファームウェアを再ビルドして配置します。

```sh
rpremote deploy examples/picoruby/projects/daisenkofun --build
```

組み込み済みコードを変えず、`main.rb`の公開設定だけを変更した場合は、通常の`rpremote run`で確認できます。詳しい手順は[開発手順](development.ja.md)を参照してください。

## トレードオフと再検討条件

mrbgem方式では、Rubyコードの変更にもビルドとファームウェア書き込みが必要です。また、組み込むコードが増えるほどファームウェア容量も使います。それでも現在は、実行時ロードの柔軟性より、長時間の安定性と再現性を優先しています。

将来、PicoRubyのファイルロードとSandboxの寿命管理が変わった場合や、実行後にパターンを追加することが作品要件になった場合は、動的ロード方式を改めて比較します。
